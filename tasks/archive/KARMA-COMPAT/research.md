# Research: KARMA-COMPAT

Дата: 2026-09-23. Ветка `feature/karma-compat`.

## Метод

Читал исходники karma (`main`) через raw.githubusercontent, код AMP в этом worktree, плюс эмпирика из разбора 2026-09-23 (AMP lite на `:19093`, 2 алерта + silence). Сам бинарник karma не запускался: `docker pull ghcr.io/prymitive/karma` → `denied` (см. F7). Всё, что помечено «по коду», — вывод из чтения, не наблюдение.

## Findings

### F1. karma берёт версию из `/metrics`, а не из `/api/v2/status`

`internal/verprobe/verprobe.go`: парсит экспозицию через `expfmt.NewTextParser`, ищет `alertmanager_build_info` и в нём лейбл `version`. Вызывается из `internal/alertmanager/models.go:77 probeVersion()` на КАЖДОМ цикле опроса (`Pull()`, `models.go:335-340`), а результат передаётся в `pullSilences(version)` и `pullAlerts(version)`.

Дальше `internal/mapper/mapper.go`:
- `latestIfEmpty("")` → `"999.0"` — пустая версия трактуется как «самый свежий Alertmanager»;
- `fixSemVersion(v)` → `strings.SplitN(v, "-", 2)[0]` — всё после первого дефиса отбрасывается;
- `GetAlertMapper` / `GetSilenceMapper` перебирают мапперы и берут первый, чей `IsSupported` вернул true; если ни один — **ошибка**, и `Pull()` делает `clearData()` + `setError()` (`models.go:111-118, 165-172`).

Единственный маппер (`internal/mapper/v017/{alerts,silences}.go:19-23`) гейтит `semver.NewConstraint(">=0.22.0")` над `semver.MustParse(version)`.

### F2. 🔴 Наивная реализация не улучшит, а сломает karma

`go-app/Makefile:33`: `VERSION ?= $(shell git describe --tags --always --dirty || echo dev)`. Сейчас на этой ветке это даёт **`v0.0.2-513-g383ce8c`** (последние теги — `v0.0.1`/`v0.0.2` от 2025-12).

Если положить `buildinfo.Version` в `alertmanager_build_info{version=...}` как есть:
`v0.0.2-513-g383ce8c` → `fixSemVersion` → `v0.0.2` → `0.0.2 >= 0.22.0` = **false** → мапперов нет → karma очищает данные и показывает ошибку `can't find alert mapper for Alertmanager v0.0.2-513-g383ce8c`.

То есть сегодня karma (по коду) работает с AMP **именно потому, что проба версии не удаётся** и срабатывает fallback `999.0`. Добавление метрики «как есть» — регресс с «работает» на «не работает». Это главный вывод исследования, и он переворачивает наивную постановку задачи.

### F3. Дефолт `"dev"` — риск паники в karma

`go-app/internal/buildinfo/buildinfo.go:10`: `Version = "dev"` при сборке без ldflags (`go run`, `go test`, ad-hoc `go build`). `IsSupported` зовёт `semver.MustParse("dev")`, а `MustParse` паникует на невалидном вводе. `recover` в пути `Pull()` я не нашёл (поиск по репозиторию karma результатов не дал, но code search без авторизации ненадёжен — считать «вероятно, паника роняет процесс», не «доказано»).

Практический вывод: значение в этой метрике обязано быть валидным semver **всегда**, включая dev-сборки. Это жёсткий инвариант, а не пожелание.

### F4. Куда регистрировать — механика есть, конфликтов нет

- `/metrics` = `promhttp.Handler()` поверх `prometheus.DefaultGatherer` (`internal/application/router.go:59`), а `pkg/metrics/v2.NewRegistry` по умолчанию пишет в `prometheus.DefaultRegisterer` (`registry.go:82`). Новый коллектор в дефолтном регистре попадёт в выдачу без изменений роутинга.
- Namespace `alert_history` (`registry.go:33`) применяется по группам метрик, а не глобально ⇒ метрика без префикса — законное additive-изменение, ничего не переименовывается.
- `github.com/prometheus/common v0.66.1` — **прямая** зависимость, то есть `version.NewCollector("alertmanager")` доступен и даёт ровно upstream-форму `alertmanager_build_info{branch,goversion,revision,tags,version}`. Подвох: этот коллектор читает пакетные переменные `common/version.*`, поэтому двумя такими коллекторами с РАЗНЫМИ значениями (compat-версия и своя) воспользоваться нельзя — один из двух придётся собрать руками (`GaugeFunc`/const-метрика, ~20-30 строк).
- Метрики `build_info` в коде сейчас нет вообще (grep пустой).

### F5. Поведение при выключенных метриках

`metrics.enabled: false` → `ExpositionGate` отдаёт **404** (`pkg/metrics/v2/exposition_gate.go:50-58`) → проба karma не удаётся → fallback `999.0` → karma продолжает работать. То есть выключение метрик karma не ломает, но и версию скрывает. Отдельно: `metrics.path` процессом не читается (известный `W603`), `/metrics` захардкожен в роутере — karma ожидает именно его, так что совпадение случайное, но рабочее. Стоит зафиксировать в доке.

### F6. Куда встраивать проверку — прецеденты есть

- `scripts/release-gate.sh` умеет необязательные шаги: `skip_step "amtool-compat" "docker not available"` (`:217`) при `docker_available()==false` (`:145-147`). Это готовый образец для karma-шага.
- Тот же шаг уже тянет **сторонний образ из внешнего registry** — `quay.io/prometheus/alertmanager:v0.34.0` (`:150`, запуск `:187-189`). Прецедент «внешний образ в гейте» создан не нами.
- `deploy/smoke/run.sh` — bash + docker compose, `trap cleanup EXIT`, бюджет «<2min на тёплом кеше» (`:10-11`), ожидание через `wait_for_http` (`:95-104`). Опциональных шагов внутри нет; skip оформлять по образцу гейта, а не здесь.
- Контрактных тестов поверх текста `/metrics` в репозитории нет: `exposition_gate_test.go` проверяет гейт на заглушечном хендлере, а не реальные имена метрик. То есть тест на экспозицию будет первым в своём роде (инструменты есть: `expfmt` из `prometheus/common`, `testutil` из `client_golang`).

### F7. Доступность образа karma (supply chain)

- `ghcr.io/prymitive/karma` в этой среде не тянется: `denied` и для `:latest`, и для `:v0.133`. При этом `quay.io/prometheus/alertmanager:v0.34.0` тянется нормально ⇒ блокируется именно ghcr, а не сеть.
- На Docker Hub есть `lmierzwa/karma` — 127 тегов, `v0.133` от 2026-09-21, `latest` от 2026-09-22, то есть зеркало идёт вровень с релизами (Lukasz Mierzwa — автор karma). **Но в README karma задокументирован только ghcr**, Docker Hub там не упоминается ⇒ формально это недокументированное зеркало, и его использование — решение по supply chain, которое принимает владелец репозитория, а не я.
- Глобальное правило карантина 7 дней: `v0.133` (2 дня) под карантином, `v0.132` (2026-08-05) — нет. Если karma-шаг вообще появится, пин — `v0.132`.

## Варианты решения (главная развилка — что класть в `version`)

| # | Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|---|
| A | Отдавать `buildinfo.Version` как есть | «Честно» и просто | Ломает karma (F2), паникует на `dev` (F3) | ❌ отклонить |
| B | `alertmanager_build_info{version}` = **compat-версия upstream-контракта** (константа `0.27.0`), плюс отдельная `amp_build_info` с реальной сборкой | karma и экосистема работают; своя версия не теряется, а публикуется под своим именем; семантика совпадает с тем, что метрика значит у upstream — «какой Alertmanager-контракт вы получаете» | Нужно руками собрать один из двух коллекторов (F4); формально заявляем контракт, который обязаны держать | ✅ **рекомендую** |
| C | B + конфиг-ключ `compatibility.alertmanager_version` | Escape hatch, если инструменту нужна версия повыше | Ключ без реального use case — против Simplicity Gate | 🔸 в BACKLOG, не сейчас |
| D | Санитизировать свою версию до semver (`v0.0.2`) | Минимум кода | `0.0.2 < 0.22.0` — ломает ровно так же, как A | ❌ отклонить |
| E | Ничего не экспортировать, только задокументировать, что karma работает | Ноль кода | Шум `Error while discovering version` каждый цикл; работоспособность держится на fallback'е, который существует только потому, что проба падает | ❌ отклонить |

Почему именно `0.27.0`: `docs/ALERTMANAGER_COMPATIBILITY.md:5` уже заявляет **«Alertmanager Version: v0.27+ (API v2)»** — то есть обещание дано, и метрика его лишь делает машиночитаемым, а не расширяет. Брать `0.28.x` было бы заявкой на фичи 0.28, которых AMP не проверял.

Лейблы у compat-метрики: `version` — константа, `revision`/`branch`/`goversion` — реальные, из `buildinfo` и рантайма. Это не подлог: метрика отвечает «какой контракт», остальные лейблы отвечают «чей билд».

## Риски

1. **Заявленная совместимость становится обязательством.** `version=0.27.0` означает, что любой инструмент включит кодовые пути 0.27. Там, где AMP отличается (data plane через K8s Secrets, известные гэпы), расхождение станет заметнее. Смягчение: раздел в compat-доке с явным «что не работает», и `amp_build_info` рядом.
2. **Тест на semver-инвариант обязателен.** Без него любая правка ldflags или дефолта снова положит karma (F2/F3). Тест должен проверять не «метрика есть», а «значение парсится как semver и проходит `>=0.22.0`».
3. **Karma-шаг в гейте зависит от недоступного registry.** При текущем окружении шаг будет постоянно уходить в skip, то есть давать ложное ощущение покрытия. Смягчение: обязательный хермет-тест на экспозицию + karma-шаг как opt-in.
4. **`semver` сейчас indirect-зависимость** (`go.mod:44`). Если тест будет использовать constraint-проверку, зависимость станет прямой. Альтернатива — сравнивать major/minor вручную и не трогать go.mod.

## Рекомендация для `/spec`

1. Вариант **B**. Константа compat-версии `0.27.0` рядом с `internal/buildinfo` (или в нём) с комментарием, что число привязано к `ALERTMANAGER_COMPATIBILITY.md:5` и меняется вместе с ним.
2. Две метрики: `alertmanager_build_info` (compat) и `amp_build_info` (реальная сборка, через `version.NewCollector` или руками — решить в спеке).
3. Обязательный хермет-тест: поднять `promhttp` поверх дефолтного регистра, распарсить экспозицию `expfmt`, достать `version`, проверить semver и `>=0.22.0` — ровно то, что делает `verprobe` + `IsSupported`. Это тест на контракт karma, а не на наличие строки.
4. karma-шаг в smoke/гейте — **opt-in и отдельным решением**: нужен ваш ответ по источнику образа (ghcr недоступен; Docker Hub `lmierzwa/karma` работает, но в доке karma не значится). Пин `v0.132` из-за карантина.
5. Вне скоупа и в BACKLOG: `versionInfo.version` в `/api/v2/status` (karma его не читает, но семантика та же — стоит решить отдельно), `metrics.path`/`W603`, унификация префиксов `alert_history_*` ↔ `amp_*`, конфиг-ключ из варианта C.

## Изменил ли research скоуп

**Да, существенно.**

- Было: «добавить метрику, чтобы убрать шум в логах karma». Стало: «не сломать karma, добавив метрику» — F2 показывает, что прямолинейная реализация даёт регресс с рабочего состояния на нерабочее.
- Появилась вторая метрика (`amp_build_info`) и константа compat-версии — то есть решение о том, как AMP представляется экосистеме. Это тянет на строку в `DECISIONS.md`, а не только на код.
- Сквозная проверка karma понижена в статусе: из «добавить в smoke» в «opt-in, при вашем решении по образу», а её место занимает хермет-тест на экспозицию.
- Оценка: ~0.5d остаётся реалистичной для кода + теста + доки; karma-шаг в гейте — отдельные ~0.25d, если решим его делать.
