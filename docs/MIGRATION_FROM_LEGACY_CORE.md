# Upgrading from AMP's Own Core (`cmd/server`) to v0.1.0

This guide is for an AMP installation built from `main` before 2026-11-08: the `cmd/server` binary (`/app/amp`, port 8080) and its Helm chart (a Deployment, `configFile.content`, Redis/Valkey state). v0.1.0 replaces that core with the upstream Alertmanager packages ([ADR-019](06-planning/DECISIONS.md)): the only binary is `amp-upstream`, the chart runs a StatefulSet, and routing, silences and HA are upstream's.

Fresh installs do not need this guide: start from [README.md](../README.md) and [helm/amp/README.md](../helm/amp/README.md).

## What changes

| Area | Before (`cmd/server`) | v0.1.0 (`amp-upstream`) |
|---|---|---|
| Binary, image | `/app/amp`, port 8080, `ghcr.io/ipiton/amp-config-reloader` sidecar | `/app/amp-upstream`, port 9093 (API), 9094 (gossip), no sidecar |
| Configuration | one file (`AMP_CONFIG_FILE`, chart `configFile.content`) with `route:`, `receivers:` and AMP keys | upstream `alertmanager.yml` (`--config.file`, chart `alertmanager.config`) plus the AMP file (`--amp.config.file`, generated by the chart) |
| Silences | PostgreSQL table `silences` | upstream snapshot on the pod volume `data` (`--storage.path`) |
| Groups, timers, notification log | Redis/Valkey | upstream, in memory plus the `data` snapshot; gossiped between replicas |
| HA | Redis locks, heartbeat, leader election | upstream memberlist cluster (`alertmanager.replicas` > 1) |
| Health | `/health`, `/healthz`, `/ready`, `/readyz` | `/-/healthy`, `/-/ready` only |
| AMP API | `/api/v1/*` | `/api/amp/v1/*` (`/api/v1/*` answers `410`, as upstream) |
| UI | AMP dashboard (`/`, `/dashboard*`) | none in v0.1.0: karma, Grafana or amtool |

Alert history, investigations and classification stay in the same PostgreSQL database; the schema only gains a column and an index.

## Before you start

- Helm ≥ 3.14 (for `--reset-then-reuse-values`). Helm 4 works too.
- A PostgreSQL dump: `helm/amp/docs/POSTGRESQL_RESTORE_GUIDE.md` § Backup.
- A quiet window. The upgrade deletes the Deployment and creates the StatefulSet: delivery pauses until the new pod is ready, and for a short while both run, so a group may be notified twice.
- `amtool` (from the Alertmanager release you trust) on your workstation.
- Note your release name and namespace; below they are `amp` and `monitoring` (so `<fullname>` is `amp`).

## Step 1. Export silences from the running old AMP

The new core does not read the `silences` table. Export the active silences while the old AMP still serves them:

```bash
kubectl -n monitoring port-forward deploy/amp 8080:8080 &
amtool --alertmanager.url=http://127.0.0.1:8080 silence query -o json > silences.json
jq length silences.json
```

`silence query` returns active and pending silences, not expired ones. With basic auth on, pass `--http.config.file` with the credentials.

Already upgraded? The table is still there (migrations never drop it). Build the same file from PostgreSQL:

```sql
\copy (SELECT coalesce(json_agg(json_build_object(
    'matchers', (SELECT json_agg(json_build_object(
        'name', m->>'name', 'value', m->>'value',
        'isRegex', (m->>'type') IN ('=~', '!~'),
        'isEqual', (m->>'type') IN ('=', '=~')))
      FROM jsonb_array_elements(s.matchers) m),
    'startsAt', s.starts_at, 'endsAt', s.ends_at,
    'createdBy', s.created_by, 'comment', s.comment)), '[]')
  FROM silences s WHERE s.ends_at > now()) TO 'silences.json'
```

## Step 2. Convert the Helm values

`--reuse-values` would keep the old chart's values, which have no `alertmanager.*` section; the render then fails with `values of a chart before UPSTREAM-CORE-REMOVAL (no alertmanager.* section)`. A removed key left in your values file also fails the render and names its replacement, for example `configFile is no longer read since UPSTREAM-CORE-REMOVAL: routes and receivers go to alertmanager.config ...`.

| Old key | v0.1.0 |
|---|---|
| `configFile.content` → `route:`, `receivers:`, `inhibit_rules:`, `templates:`, `time_intervals:`, `global:` | `alertmanager.config` (a YAML map, read as upstream `alertmanager.yml`) |
| `configFile.content` → `database:`, `llm:`, `investigation:`, `publishing:`, `server.auth` | chart values `externalDatabase.*`, `llm.*`, `investigation.*`, `publishing.*`; anything else under `alertmanager.ampConfig` |
| `configFile.enabled`, `.mountPath`, `.fileName` | remove |
| `configReloader.*` | remove: a values change rolls the pods (checksum); without Helm, `POST /-/reload` or `SIGHUP` |
| `replicaCount`, `autoscaling.*` | `alertmanager.replicas` (no HPA) |
| `strategy.*` | remove: the StatefulSet rolls pods one at a time |
| `upstreamCore.*` (preview of slice 4) | `alertmanager.*` (same sub-keys) |
| `server.externalUrl` | `alertmanager.externalURL` |
| `grouping.*` | `group_by`, `group_wait`, `group_interval`, `repeat_interval` on the root `route:` in `alertmanager.config` |
| `silencing.*`, `storage.*`, `persistence.*`, `liteProfile.*` | `alertmanager.persistence` (size, storage class of the `data` volume) |
| `cache.*` | remove: `amp-upstream` uses no cache |
| `logLevel` | remove: no log level flag |
| `alerts.*`, `migration.*` | remove: migrations run at start |
| `publishing.queue`, `publishing.templates`, `publishing.health`, `publishing.refresh.*` other than `interval` | remove (ignored): delivery is upstream's |
| `llm.retryDelay`, `llm.cacheTtl`, `llm.batchSize` | remove (ignored) |
| `gracefulShutdown.timeoutSeconds` | remove: shutdown drains HTTP for 5s; keep `gracefulShutdown.terminationGracePeriodSeconds` |
| `service.port: 8080`, `service.metricsPort` | `service.port` defaults to 9093; `/metrics` is on the same port |
| `probes.*.path: /healthz`, `/readyz` | `/-/healthy`, `/-/ready` (the defaults) |

Keys that keep their meaning: `profile`, `environment`, `image.*`, `postgresql.*`, `externalDatabase.*`, `llm.enabled`/`provider`/`proxyUrl`/`apiKey`/`model`/`timeout`/`maxRetries`, `investigation.*`, `publishing.enabled`/`discovery.*`/`refresh.interval`, `webConfig.*`, `ingress.*`, `networkPolicy.*`, `monitoring.*`, `extraVolumes`, `extraVolumeMounts`, `valkey.*`, `serviceAccount.*`, `podDisruptionBudget.*`, `resources`, scheduling.

Before:

```yaml
replicaCount: 2
logLevel: info
grouping:
  enabled: true
server:
  externalUrl: https://amp.example.com
configFile:
  enabled: true
  content: |
    global:
      resolve_timeout: 5m
      group_wait: 30s
    route:
      receiver: slack
      group_by: [alertname, namespace]
    receivers:
      - name: slack
        slack_configs:
          - api_url_file: /etc/amp/secrets/slack-webhook-url
            channel: '#alerts'
    llm:
      enabled: true
```

After (`values-v0.1.0.yaml`):

```yaml
llm:
  enabled: true
  apiKey: ""            # or llm.externalSecrets / externalSecrets.enabled, as before
alertmanager:
  replicas: 2
  externalURL: https://amp.example.com
  config:
    global:
      resolve_timeout: 5m
    route:
      receiver: slack
      group_by: [alertname, namespace]
      group_wait: 30s
    receivers:
      - name: slack
        slack_configs:
          - api_url_file: /etc/amp/secrets/slack-webhook-url
            channel: '#alerts'
extraVolumes:
  - name: receiver-secrets
    secret:
      secretName: amp-receiver-secrets
extraVolumeMounts:
  - name: receiver-secrets
    mountPath: /etc/amp/secrets
    readOnly: true
```

Check the render before touching the cluster:

```bash
helm template amp ./helm/amp -n monitoring -f values-v0.1.0.yaml --set llm.apiKey=dummy > /dev/null && echo OK
```

## Step 3. Check `alertmanager.yml` against upstream

Upstream parses `alertmanager.yml` strictly: an unknown key fails the start, and `POST /-/reload` rejects it with the previous config kept.

- `global.group_by`, `global.group_wait`, `global.group_interval`, `global.repeat_interval` were AMP extensions and now fail with `field group_wait not found in type config.plain`. Move them to the root `route:`; child routes inherit them.
- A route without `group_by` puts all its alerts into one group, as upstream does. If you relied on per-`alertname` grouping, set `group_by: [alertname]`.
- `email_configs` need `global.smtp_smarthost` and `smtp_from` (or a `from` per entry), as upstream.
- All 18 upstream integrations are available, including `opsgenie_configs`, `victorops_configs` and `wechat_configs`, which the old core accepted and dropped.

Validate the file with the same parser:

```bash
yq '.alertmanager.config' values-v0.1.0.yaml > alertmanager.yml
amtool check-config alertmanager.yml
```

## Step 4. Large `alerts` table: build the index first

At start `amp-upstream` adds `alerts.upstream_fingerprint` and builds `idx_alerts_upstream_fingerprint` `CONCURRENTLY`, within one minute. The table has one row per label set ever seen and no retention. Check its size; on a large table build the index before the upgrade, or history and investigations stay off until a restart:

```sql
SELECT count(*) FROM alerts;
ALTER TABLE alerts ADD COLUMN IF NOT EXISTS upstream_fingerprint VARCHAR(16);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_alerts_upstream_fingerprint ON alerts(upstream_fingerprint);
```

Run each statement on its own (`psql -c` with several statements is one transaction, and `CONCURRENTLY` refuses it). The migrations use the same `IF NOT EXISTS`, so they skip what you created. An INVALID index left by an interrupted build is reported at start (`alert history: index idx_alerts_upstream_fingerprint is missing or INVALID`); drop it with `DROP INDEX CONCURRENTLY idx_alerts_upstream_fingerprint;` and create it again.

## Step 5. Upgrade

```bash
helm upgrade amp ./helm/amp -n monitoring --reset-then-reuse-values -f values-v0.1.0.yaml
kubectl -n monitoring rollout status statefulset/amp
```

`--reset-then-reuse-values` starts from the new chart's defaults and keeps only the values you set yourself; a removed key among them still fails the render, so the error names what to fix. Passing all your values files instead (`-f values-production.yaml -f values-v0.1.0.yaml`, no reuse flag) works too.

What the upgrade does:

- deletes Deployment `amp` and creates StatefulSet `amp` with a `data-amp-<i>` volume per pod, Services `amp` (9093) and `amp-headless` (9093, gossip 9094);
- deletes the lite profile's PVC `amp-pvc` (SQLite data of the old core); PVCs `data-amp-upstream-<i>` of a slice-4 `upstreamCore` preview stay and can be deleted;
- leaves an HPA created with `helm.sh/resource-policy: keep` by an old chart in place: `kubectl -n monitoring delete hpa amp` if it is still there;
- does not touch PostgreSQL data or the Valkey volume.

Without Helm (binary or your own manifests):

```bash
amp-upstream \
  --config.file=/etc/amp/alertmanager.yml \
  --amp.config.file=/etc/amp/amp.yaml \
  --storage.path=/data \
  --web.listen-address=:9093
```

`AMP_CONFIG_FILE` is no longer read; the AMP file is passed with `--amp.config.file` (keys: [CONFIGURATION_GUIDE.md](CONFIGURATION_GUIDE.md)). `DATABASE_PASSWORD` and `LLM_API_KEY` from the environment still override the file. Keys of the old file that `amp-upstream` does not read are logged once at start: `AMP configuration keys ignored ... "keys":["redis","server.port"]`.

## Step 6. Import the silences

```bash
kubectl -n monitoring port-forward svc/amp 9093:9093 &
amtool --alertmanager.url=http://127.0.0.1:9093 silence import < silences.json
amtool --alertmanager.url=http://127.0.0.1:9093 silence query
```

Imported silences get new IDs; links to old silence IDs stop working. Run the import **once**: the IDs in `silences.json` are unknown to the new AMP, so amtool creates each silence anew, and a second run duplicates them all (expire the extra ones with `amtool silence expire`). With several replicas, import into one pod: gossip copies them to the others.

## Step 7. Reset the Redis/Valkey state

The old core kept groups, timers and the notification log in Valkey. `amp-upstream` never reads them, so nothing has to be migrated, and nothing is carried over: after the upgrade each still-firing group is notified once more after its `group_wait`, and a resolve for an alert that cleared during the upgrade may not be sent.

The v0.1.0 chart does not deploy Valkey (`valkey.enabled: false`, kept for `UPSTREAM-AI-HA-DEDUP`): the upgrade removes its StatefulSet, Services, Secret, ServiceMonitor and alert rules, unless your values set `valkey.enabled: true`. The volume stays; to drop the old state:

```bash
kubectl -n monitoring delete pvc redis-data-amp-redis-0
```

Keep the volume if you may roll back (§ Rollback). An external cache (`cache.host`) can be decommissioned.

## Step 8. Update the clients

| Client | Change |
|---|---|
| Prometheus `alerting.alertmanagers` | port 9093; with `alertmanager.replicas` > 1 list every pod (`amp-0.amp-headless.monitoring.svc:9093`, ...), not the Service: each pod must receive every alert |
| Probes, uptime checks | `/-/healthy`, `/-/ready` (`/health*`, `/ready*` answer `404`) |
| Investigation reads | `GET /api/v1/alerts/{fingerprint}/investigation` → `GET /api/amp/v1/alerts/{fingerprint}/investigation`; `{fingerprint}` is the 16-hex one from `api/v2` (AMP's 64-hex SHA-256 also works); in the response `fingerprint` is the upstream one and AMP's SHA-256 is `amp_fingerprint` |
| Resolved alerts | `GET /api/v2/alerts?status=resolved` is ignored (the parameter is unknown upstream: you get active alerts); read one alert's record with `GET /api/amp/v1/alerts/{fingerprint}` |
| Inhibitions | `GET /api/v2/inhibitions` is `404`: use `status.inhibitedBy` in `GET /api/v2/alerts`, rules in `config.original` of `GET /api/v2/status` |
| Groups | `?group_by=` on `GET /api/v2/alerts/groups` is ignored; groups follow the routes' `group_by` |
| `POST /api/v2/alerts` | needs `Content-Type: application/json` (else `415`); errors are `400`/`422` with a JSON string body, as upstream; Prometheus and amtool already send the header |
| `GET /api/v2/alerts?active=...` | an invalid boolean is read as `false`, as upstream: check scripts that pass `yes`/`1` |
| AMP dashboard | gone: [karma](https://github.com/prymitive/karma), the Grafana Alertmanager data source or amtool ([ALERTMANAGER_COMPATIBILITY.md](ALERTMANAGER_COMPATIBILITY.md#viewing-alerts-karma-grafana-amtool)) |
| Dashboards and alerts on metrics | metrics of the old core (grouping, routing, inhibition, silences, publishing queue, `amp_config_reloader_*`) are gone; use upstream's `alertmanager_*` |

`/debug/*` (pprof, `expvar` with the process command line) is served on the API port, as upstream. Do not pass secrets in flags, and keep the port off the public network.

## Step 9. Verify

```bash
curl -s http://127.0.0.1:9093/-/ready
amtool --alertmanager.url=http://127.0.0.1:9093 config show | head
amtool --alertmanager.url=http://127.0.0.1:9093 alert query
amtool --alertmanager.url=http://127.0.0.1:9093 cluster show     # replicas > 1: every peer ready
kubectl -n monitoring logs statefulset/amp | grep -iE 'error|ignored|INVALID'
```

With `profile: standard`, `GET /api/amp/v1/alerts/<fingerprint from api/v2>` returns the alert's history row, and the log shows `alert history: upstream fingerprints backfilled` once.

## Rollback

`helm rollback amp <revision>` brings back the Deployment and the old core:

- PostgreSQL: migrations are additive; the old binary ignores the new column and index. Do not run `goose down` ([ROLLBACK_RUNBOOK.md](ROLLBACK_RUNBOOK.md)).
- Silences: the old core reads the `silences` table as it was at the upgrade; silences created on v0.1.0 are not there.
- Valkey: if you kept its volume, the old core resumes from its state; if you deleted it, every firing group notifies once more.
- The StatefulSet's `data-amp-<i>` volumes stay; delete them if you do not come back.
