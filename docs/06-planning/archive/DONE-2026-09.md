- 2026-09-24 — (TASK / Parity) **PARITY-RESOLVE-TIMEOUT-ENDSAT** — алерт, пришедший без `endsAt`, больше не отдаётся как отгоревший. Раньше `GET /api/v2/alerts`, `/api/v1/alerts` и `/api/v2/alerts/groups` отдавали `endsAt == startsAt == updatedAt` (фолбэк на `updatedAt` в `alertconv.ToGettableAlert`), и любой потребитель, судящий по `endsAt` (как сам Alertmanager), видел активный алерт резолвнутым. Теперь, как upstream: `endsAt = receivedAt + global.resolve_timeout` (дефолт 5m), повторная отправка продлевает окно, явный `endsAt` не трогается, `/-/reload` применяется к следующему POST без пересчёта сохранённых.
  - **Поправки research к исходной постановке:** upstream считает от времени приёма, а не от `startsAt` (с `startsAt + 5m` долго горящий алерт всё равно выглядел бы отгоревшим). Штамповать `core.Alert` до `ProcessAlert` нельзя: dedup считает изменение `EndsAt` поводом для update, и каждый повторный POST гнал бы БД, классификацию (LLM) и grouping. На `/spec` найдена rehydration из БД, пропущенная research'ем: без штамповки на этом пути после рестарта баг возвращался.
  - **Реализация:** штамповка в нормализации memory store (`storage/memory/alert_store.go`) на обоих путях — POST и `RestoreFromPersistence`, только firing, строго после вычисления статуса. Провайдер таймаута читает живой конфиг на каждый ingest-батч (`ServiceRegistry.newAlertStore`, `resolveTimeoutFromConfig`); фолбэк — `alertconv.DefaultResolveTimeout`. Защитный фолбэк `ToGettableAlert` для firing теперь `updatedAt + 5m`. Хендлеры не менялись; dedup, БД (`ends_at = NULL`) и нотификации видят алерт как прислан (ADR-010).
