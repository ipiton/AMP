# Changelog

All notable changes to Alertmanager++ (AMP) will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **PROD-INFRA** (2026-08-20): production Helm values audit + release-notes process (`helm/amp`, `docs/`). No Go changes.
  - **`GET /health/reload`** (new): reports the FULL reload outcome — `status`, `version`, `attempts`, `last_reload_time`, `split_state`, and the outstanding W6xx `restart_required` findings. 200 when healthy, 503 with a body saying why. `restart_required` does NOT make it unhealthy (the reload applied; a probe pointed here must not crash-loop a pod over a `metrics.path` edit), but a split state — an incomplete rollback (W610) or a failed post-commit stage (W611) — does. Deliberately not wired into any liveness/readiness probe.
  - **`cmd/config-reloader`** (new binary): polls the config file's SHA256 (content, not mtime — kubelet re-syncs a ConfigMap volume without changing the bytes), triggers a reload by `POST /-/reload` or SIGHUP, and **verifies** it against `/health/reload` before counting it a success. Metrics on `:9091`: `amp_config_reloader_reloads_total{result="success|rejected|failed|unverified"}`, `..._last_reload_timestamp_seconds`, `..._last_reload_successful` (the alertable series — a stuck ConfigMap edit sits at 0), `..._config_hash` + `..._config_info{hash}`, `..._watch_errors_total`.
  - **A rejected config is retried with capped exponential backoff**, reset by any new edit, instead of once per poll — one bad ConfigMap cannot generate a failed reload every 10s forever.
  - **`--method=signal` refuses to signal itself.** In a pod without `shareProcessNamespace: true` every container is its own PID 1, so the default `--pid=1` would deliver SIGHUP to the reloader (which ignores it) and report every reload as delivered. The binary refuses, the chart defaults to `http`, and the template refuses to render `method: signal` without the shared namespace.
  - **Two coordinator additions the verification needs**: a `no_changes` status (a comment-only edit changes the file hash but parses to an identical config — previously indistinguishable from a lost signal, because the status was left untouched) and a completed-attempt counter, so a caller can confirm *its own* trigger was processed without trusting clocks across containers. The counter increments when the OUTCOME is recorded, not when the attempt starts — the end-to-end test caught a poller reading the previous status through that window.
  - **Helm**: new `configFile` section renders the Alertmanager-shaped `config.yaml` into its own ConfigMap, mounts it read-only and sets `AMP_CONFIG_FILE`. The chart had **no config file at all** before this, so `route:`/`receivers:`/`inhibit_rules:`/`templates:` could not be expressed in it. That ConfigMap is deliberately excluded from the pod's `checksum/config` annotations: rolling the pod on every config edit is exactly what hot reload exists to avoid. New `configReloader` section (enabled/image/resources/interval/method/…) adds the sidecar container sharing the config volume; `values-production.yaml` enables it with a **secret-free** route tree, since receivers carry credentials and a ConfigMap is not the place for them.
  - **`Dockerfile.config-reloader`**: distroless static, non-root (uid 65532), no shell, read-only filesystem.
  - Chart test harness (`helm/amp/tests/render-config-reloader.sh`, the chart had none) asserts the sidecar renders off/on, is non-root and read-only, and that the three silent-failure misconfigurations are refused at render time.
  - **The sidecar ships DISABLED everywhere, including `values-production.yaml`, because no CI job builds its image yet.** `Dockerfile.config-reloader` exists but nothing publishes it, and `configReloader.image.repository` is a placeholder that must be pointed at whatever the pipeline produces. Do not set `configReloader.enabled: true` before then: pod readiness requires ALL containers, so an unpullable sidecar keeps the pod out of the Service endpoints and stalls the rollout while the `amp` container itself is healthy — enabling hot reload would take the deployment down. Flip it to `true` in the same change that adds the build job.
  - **Verification caveat on `method: signal`**: `POST /-/reload` is synchronous so the sidecar always sees the final outcome, but SIGHUP is not — if a post-commit section (routing/templates/receivers) fails and rolls the reload back, the sidecar can observe the first outcome and only re-checks best-effort. Documented next to the `method` value; do not alert on `amp_config_reloader_last_reload_successful` on a signal-method deployment until `FU-RELOAD-UNIFY-APPLIERS` lands.
  - **W6xx `Reason` is a fixed string, never a formatted cause.** `/health/reload` is unauthenticated and serves the warning verbatim, and component errors carry config content — pgx embeds `user=<user> database=<db>` and every dialed `host:port`, the routing engine echoes receiver names and matcher messages. The W610/W611 causes now go to the log only; the endpoint gets the code plus the already-structured component/stage names. Asserted by tests that fail on those substrings appearing in the response body.
  - `log.level` unset is now accepted at load time too (it means "info", as `pkg/logger` and the reload validator already agreed): `Config.Validate()` still required it, so a config with `level: ""` failed `LoadConfig` outright and the two rules contradicted each other. The agreement test now runs through `LoadConfig`, which is the path an operator's file actually takes.
  - **Contract** (`internal/config`): `Reloadable` now takes `Reload(ctx, oldCfg, newCfg)` and declares `RelevantSections()` — the `mapstructure` names of the config sections it reads (`"database"`, `"redis"`, `"log"`, `"metrics"`, `"llm"`). The reloader calls a component only when one of its sections actually differs between the two configs (`config.SectionChanged`, reflection over `Config`'s own tags), so a component never has to re-derive "did anything change". An unknown section name is treated as always-relevant and logged as an error at registration — a typo must reload loudly, never skip silently. Optional `OrderedReloadable.ReloadPriority()` fixes the order.
  - **Deterministic, fail-fast execution**: `DefaultConfigReloader` runs components **sequentially** in priority order (logger 10 → metrics 20 → llm 50 → redis 80 → database 90) instead of in parallel, and stops at the first error. The logger goes first so every later reload line is emitted at the operator's new level and format; storage goes last so the most disruptive step runs after everything cheap has succeeded.
  - **BEHAVIOUR CHANGE — any component failure now rejects the whole reload.** Previously only components on a hardcoded "critical" list triggered a rollback, and a non-critical failure was reported as an overall **success** — meaning the config the API reported was not the config in effect in that component. `IsCritical()` now only grades log/metric severity and the wording of the rejection. The rejection names the component; the previous config stays active. In practice nothing regressed at the time of the change, because the registry was empty.
  - **Five components, three of them real**: `LoggerReloadable` swaps `log.level` and `log.format` (json ↔ text) for real, via a new `pkg/logger.SwappableHandler` — loggers already derived with `With()`/`WithGroup()` follow the swap, because the derivations are replayed against the live delegate instead of being bound to the pre-swap handler. `MetricsReloadable` makes `metrics.enabled` a live switch through a new `pkg/metrics/v2.ExpositionGate` wrapped around `/metrics` (404 while closed — an empty 200 would look like a live target reporting zero). `LLMReloadable` swaps provider/base_url/api_key/model/max_tokens/temperature/timeout/max_retries atomically on the live client under a new RWMutex snapshot in `HTTPLLMClient`; one request never mixes a new base URL with an old key.
  - **Two components that refuse instead of pretending**: `DatabaseReloadable` and `RedisReloadable` carry the full machinery — build the new pool/client, verify it (`Ping`/`PING`), swap atomically, drain the replaced Postgres pool 5s then close it — but they **decline** while a raw handle is outstanding. `PostgresPool.SharePool()` / `RedisCache.ShareClient()` now mark such handles, and every long-lived consumer takes its handle that way (storage adapter, silence + investigation repositories, investigation tools `*sql.DB`; leader election, cluster heartbeat, silence event bus, group storage, notification log, timer storage). Those consumers captured the pointer at construction and cannot follow a swap: closing the old pool/client would break them, and swapping only the wrapper would split writes across two databases or split claim TTLs and delivered-state across two Redis keyspaces. So in the standard profile **every `database.*` and `redis.*` edit reports restart-required** — the honest state of the wiring. Follow-ups `FU-DB-LIVE-POOL-HANDLE` / `FU-REDIS-LIVE-CLIENT-HANDLE` reduce that to a wiring change.
  - **W6xx restart-required warnings**: a change that cannot be applied live raises a codified, greppable warning naming the **field paths only, never values** — `W600` database, `W601` redis, `W602` log output/rotation (`log.level`/`log.format` are applied live), `W603` `metrics.path`/`metrics.port` (never read by the process, so a restart will not apply them either), `W604` `llm.enabled`/`llm.agent_mode` (they decide whether the investigation pipeline is built at all). Deliberately disjoint from `pkg/configvalidator`'s W1xx–W3xx, which are *validation*-time findings. Queryable via `ServiceRegistry.RestartWarnings()`, cleared at the start of each reload attempt; slice 2 exposes them on `/health/reload`.
  - **`cfg.Log` is now honoured at startup.** `cmd/server/main.go` hardcoded JSON/info and never read the `log:` section at all, so `log.level: debug` did nothing even across a restart. It now installs the swappable handler and applies `log.level`/`log.format` as soon as config is loaded; an unsupported format is logged and ignored rather than fatal.
  - **Fixed while wiring**: `identifyAffectedComponents` consulted only `diff.Modified` (so adding a whole `redis:` section flagged nothing) and had no mapping for `log`/`metrics` (so the logger and metrics components would have been gated out whenever another section changed in the same edit).
  - Startup and reload now build pool/client configs through the same `PostgresConfigFrom`/`CacheConfigFrom` helpers, so a reload cannot silently change a knob the operator never edited.
  - **Operational note on `metrics.enabled`**: it used to be inert. If your values file sets it to `false` — which previously did nothing — `/metrics` now returns **404** and your scrape target goes down. The shipped default is `true` and no shipped values file overrides it.
  - **Fix round (slice-1 review: 1 Critical, 4 Important, 9 Minor)**:
    - **`llm.*` reload reached only half the process.** `initializeClassification` and `initializeInvestigation` each built their own, identically-configured `*HTTPLLMClient`, and only the investigation one was registered — so an `llm.model`/`llm.api_key` edit reported success while **every alert classification**, the higher-traffic path, kept the old model and the old credential (401s behind an HTTP 200 on a key rotation). There is now exactly one client per process; any future LLM consumer must take it from `sharedLLMClient()`. Behaviour-neutral for the circuit breaker — only `ClassifyAlert` routes through it.
    - **`log.output`/`log.filename`/rotation are now genuinely applied at startup.** `pkglogger.SetupWriter` had no caller in the server binary, so the process always logged to stdout while W602 told operators to restart to apply those fields — the same dead-config defect W603 correctly reports for `metrics.path`/`port`. The handler is now built over `SetupWriter(LoggerConfigFrom(cfg.Log))` once config is loaded, so the warning became true rather than being reworded.
    - **A declined (restart-required) change is now durable.** Previously the decline returned nil, the coordinator committed the config anyway, the next diff saw no change to that section, and the warning was cleared at the start of the next reload — so an operator's unapplied edit disappeared from the record while the process kept running the old value. Each component now tracks the config it has **actually applied** and re-raises its warning on every attempt while they differ (new optional `config.ResyncReloadable` lets a drifted component be selected past both the name and the section gate); reverting the edit resolves the warning with no restart. Each component also records at most **one** warning per attempt — the collector is keyed by code+component, so the old two-`Record` paths silently overwrote each other.
    - **A failing rollback no longer abandons the remaining components.** Rollback reused the fail-fast forward path, so a rollback failing at component K left every later component on the rejected config with no record. It is best-effort now, and a non-empty failure set raises **W610** naming the diverged components (never resolved by a config edit — only a restart) plus an error that says which components are split.
    - **A post-commit applier failure now rolls the reload back.** `routing`/`templates`/`receivers`/`inhibition` are applied by `ServiceRegistry` after the coordinator commits; a routing failure used to return "reload failed" to the operator while the new config was fully live in all five components. It now restores both config views, drives the components back, records **W611** naming the stage, and returns an error that says it rolled back. Folding those appliers into the component registry, so one failure policy and one rollback path cover everything, is `FU-RELOAD-UNIFY-APPLIERS`.
    - Minors: `SharePool`/`ShareClient` take the reload mutex so the guard is airtight rather than merely unreachable; `RedisCache.Reload`'s "no drain needed" claim now states what it does not cover (blocking commands, pub/sub) and that a drain window becomes mandatory with `FU-REDIS-LIVE-CLIENT-HANDLE`; `RedisCache.isClosed` is atomic; the unbounded pool-drain goroutine, the `Enabled()`/`Handle()` swap window, and the un-restarted health-check period are documented; handler benchmarks added for the plain and derived paths.
  - **`helm/amp/values-production.yaml` audited against the running app**, not just against BACKLOG's wishlist: every viper default the alertmanager-parity waves added (`publishing.queue.delivery_confirmation_timeout`, `publishing.templates.enabled`, `grouping.reconciliation_interval`/`reconciliation_grace`, `storage.path`/`snapshot_interval`, `silencing.subscribe_retry_backoff`/`periodic_resync_interval`) now has a values-shape home in `values.yaml` and a production-tuned value or an explicit "why not set" comment in `values-production.yaml`, wired end-to-end into `templates/configmap.yaml` (viper's `AutomaticEnv` + `.`→`_` env key replacer, so a rendered `ConfigMap` key genuinely reaches the process — several of these were previously values with no template consumer at all).
  - **Two claims in the old `values-production.yaml` didn't match what the chart's templates actually do, and are corrected rather than carried forward**: BACKLOG's "PostgreSQL cluster (3 instances)" — `templates/postgresql-statefulset.yaml` is a single-primary StatefulSet with no replication/failover; the old `postgresql.cluster.*` keys rendered nothing (no template read them), and setting `replicas: 3` on that template would start three uncoordinated, non-replicating Postgres processes sharing no data (split-brain), not a cluster. And "DragonflyDB cache" — no `dragonfly-*.yaml` template exists; DragonflyDB is Redis-wire-compatible and is now wired the way the app actually reads its cache endpoint (`cache.host`/`cache.port`/`cache.auth`, already bound to `REDIS_ADDR`/`REDIS_PASSWORD` in `templates/deployment.yaml`) instead of through a dead `dragonfly:` values block.
  - **Two chart bugs found and fixed while making the above true**: `templates/redis-statefulset.yaml`'s `replicas: {{ .Values.valkey.replicas | default 1 }}` made `valkey.replicas: 0` (the only override that can disable the chart's own in-cluster Redis/Valkey when an external cache is used) silently render as `1` — Helm/sprig's `default` treats an explicit `0` as empty; fixed to `{{ .Values.valkey.replicas | int }}`. New `templates/poddisruptionbudget.yaml` + `podDisruptionBudget` values (disabled by default, enabled in production) — the app `Deployment` had no PDB at all despite `autoscaling`/anti-affinity already assuming HA.
  - **`values-production.yaml` password hygiene, corrected description**: this file never carried its own `postgresql.password` key — the weak literal placeholder lives in the base chart's `values.yaml` (still there, ledgered in `docs/06-planning/TECH-DEBT.md`) and was silently INHERITED by any `helm install -f values-production.yaml` that didn't separately override it (a `-f` file layers on top of the chart's own `values.yaml`, not instead of it). The new explicit `postgresql.password: ""` in this file shadows that inherited weak default — `templates/postgresql-secret.yaml` has no random-generation fallback for this key, so leaving it blank fails obviously (empty-password Secret, Postgres itself then refuses to start) instead of silently keeping the weak credential. `cache.auth.password` gets a stricter version of the same intent: `templates/secret.yaml`'s redis/valkey credential DID have a `default (randAlphaNum 32)` fallback that would have silently baked in a random password mismatched against a real external DragonflyDB — fixed with a `required` guard (fix-round finding C1) instead of relying on emptiness alone, since an empty value there was rendering successfully with a plausible-looking wrong secret, not failing.
  - **Remaining chart gaps, not fixed, ledgered instead** (`docs/06-planning/TECH-DEBT.md`): `valkey.enabled`/`cache.enabled` still don't gate `redis-statefulset.yaml`'s deployment (only `profile: standard` does) — `valkey.replicas: 0` is documented as the working override, not a real fix; `postgresql.existingSecret` is read by the app's own `secret.yaml` but ignored by `templates/postgresql-secret.yaml`/`amp.postgresql.secretName`, so it has no effect on the credential the app and the StatefulSet actually use.

- **TEMPLATES-EPIC** (2026-08-19): **upstream-compatible notification templates** — the last functional drop-in gap. `templates:` files and per-integration presentation fields now RENDER, instead of being parsed and ignored. Closes `FU-INTEGRATION-FIELD-FIDELITY` in the same pass.
  - **Engine + data model** (`internal/business/templating`): a faithful port of `prometheus/alertmanager@v0.34.0`'s `template/template.go` — upstream's `Data` (`Receiver`, `Status`, `Alerts` with `.Firing`/`.Resolved`, `GroupLabels`, `CommonLabels`, `CommonAnnotations`, `ExternalURL`), the `KV`/`Pairs`/`Strings` helpers with upstream's `alertname`-first `SortedPairs` ordering, and all **25** `DefaultFuncs` (none skipped; `title` and `humanizeDuration` reuse `x/text` and `prometheus/common` so their output is byte-identical). Alert fingerprints use the upstream 16-hex form. Apache-2.0 notices retained per file.
  - **Default template library**: `default.tmpl` and `email.tmpl` copied **byte-for-byte** from upstream v0.34.0 (checksums recorded in `internal/business/templating/templates/NOTICE`), so `slack.default.title`, `pagerduty.default.description`, `email.default.subject`/`html`, `telegram.default.message` and every helper they reference resolve exactly as upstream's do.
  - **`templates:` config section**: globs loaded at config load and on `/-/reload`, resolved relative to the **config file's directory** (upstream's `resolveFilepaths`), later definitions overriding earlier ones and user files overriding the shipped defaults. A malformed template file is a **config load error naming the file and the line**. A glob matching nothing stays legal (a ConfigMap may mount after startup) but logs a WARNING naming the resolved glob, so a wrong path is visible instead of silent.
  - **Per-integration template fields reaching the wire**: `slack_configs[].title`/`title_link`/`pretext`/`text`/`color`/`username`/`icon_emoji`/`icon_url`/`channel`, `pagerduty_configs[].description`/`severity`/`client`/`client_url`/`details.*`, `telegram_configs[].message`, `email_configs[].subject`/`html`/`text`/`headers.*`. Upstream's own defaults are materialized when a field is unset, so an untouched upstream config renders upstream's output without naming a single field. `webhook_configs` is deliberately not templated — upstream does not template webhook payloads either, and AMP's v4 batch marshaling is untouched.
  - **Reload safety**: the live template library is swapped atomically, so a render in flight always sees one complete generation, and a reload whose files are broken keeps the last-known-good library rather than reverting to bare defaults.
  - **Observability**: `alert_history_publishing_template_renders_total{integration,outcome}`, `alert_history_publishing_template_fallbacks_total{integration,reason}` (`exec_error`/`timeout`/`output_cap`/`not_defined`), and `alert_history_publishing_template_abandoned_executions` / `..._in_flight_abandoned_executions`.
  - **Kill switch**: `publishing.templates.enabled` (default `true` = upstream rendering). `false` restores AMP's pre-epic fixed formatters wholesale — no template library is built, no publisher is decorated, and `templates:` files plus every per-integration presentation field are ignored exactly as before this epic. Read at startup; a change needs a restart, not a reload.
  - **Guards upstream does not have** (deliberate divergence, in AMP's favour): every render is bounded by a timeout and an output cap — `publishing.templates.render_timeout` (default `5s`) and `publishing.templates.max_output_bytes` (default 4 MiB) — and panics are recovered. Exceeding a guard **never drops a notification**: AMP's fixed formatter output is delivered instead and the fallback is counted.

  **Migration notes — note 1 is a BREAKING CHANGE for every deployment that uses `route:`/`receivers:`, whether or not you configured a single template:**
  1. **BREAKING: your Slack and email notifications change shape by default.** Upstream's presentation defaults are materialized for every unset field of every `receivers:`-provisioned `slack_configs`/`pagerduty_configs`/`telegram_configs`/`email_configs` entry, and the template renderer is wired unconditionally — so a config that names no template at all now renders **upstream's** output instead of AMP's. Concretely, before → after:
     - **Slack**: AMP's Block Kit message (a `blocks` array with AMP-worded sections) → upstream's `attachments` shape — `title` = `[FIRING:1] <group labels> (<remaining common labels>)`, `title_link` + `fallback` = the alertmanager link, top-level `text` = upstream's fallback string, plus a new `username: "Alertmanager"`. The `blocks` array is **gone**.
     - **Email**: AMP's own subject and HTML body → upstream's `email.default.subject` and its ~10 KB `email.default.html`.
     - **PagerDuty / Telegram**: `summary`/`client`/`client_url` and the message body become upstream's `pagerduty.default.*` / `telegram.default.message` renderings; PagerDuty `custom_details` gains upstream's `firing`/`resolved`/`num_firing`/`num_resolved` entries on top of AMP's diagnostics.
     - **Webhook**: unchanged. Upstream does not template webhook payloads, and neither does AMP.
     - **Kubernetes-Secret-provisioned targets**: unchanged. Discovery does not populate template fields, so those targets keep the fixed formatters.

     This is the drop-in parity the epic exists for — an untouched upstream config should render upstream's output — but it IS a visible change for anyone who migrated a config and got used to AMP's formatting. **The revert is one line:** `publishing.templates.enabled: false` restores the pre-epic fixed formatters wholesale (`templates:` files and per-integration presentation fields ignored, exactly as before). It is read at startup, so flipping it needs a restart, not a reload.
  2. **A receiver that DOES name presentation fields renders your content, not both.** For Slack the operator's presentation replaces the Block Kit rendering rather than shipping two versions in one message. If you want AMP's formatting for a specific integration, use the switch in note 1 — removing the fields no longer restores it, because the defaults are materialized.
  3. **Relative `templates:` paths now work** (`templates: ['templates/*.tmpl']`, upstream's canonical idiom) and resolve against the config file's directory. Previously they resolved against the process CWD, matched nothing, and loaded clean — if you worked around that with absolute paths, those still work unchanged.
  4. **A broken template file now fails config load** instead of being ignored. Validate with a reload against a copy before rolling out.
  5. **`{{ .Alerts }}` holds ONE alert per message for slack/pagerduty/telegram/email** — a DELIVERY divergence, not just a data-model one. Upstream sends one message per group; AMP sends one per alert, each with a one-element `.Alerts`. A migrated `{{ range .Alerts }}` template that upstream rendered as a single aggregated message therefore arrives as N single-alert messages. Group labels, receiver and status are correct; the alert SET is not upstream's. Webhook delivery is unaffected (it batches the whole group, upstream's v4 shape).
  6. `{{ .RouteLabels }}`, `{{ routeLabels "x" }}` and `{{ .NotificationReason }}` are accepted and render **empty** — AMP has no source for them. They do not error, so a migrated template using them keeps working.
- **AMP-PARITY-WAVE6-EPIC** (2026-08-19): `FU-RECEIVERS-INTEGRATION` — **`receivers:` integrations now provision delivery endpoints**, closing the epic's control-plane/data-plane split. An untouched upstream `alertmanager.yml` delivers with **zero Kubernetes Secrets**.
  - **Auto-provisioning** (`internal/business/publishing/config_targets.go`): every `webhook_configs` / `slack_configs` / `pagerduty_configs` / `telegram_configs` / `email_configs` block becomes an in-memory `core.PublishingTarget` named `cfg:<receiver>/<type><idx>`, scoped to its receiver by construction, encoded EXACTLY the way K8s-Secret-sourced targets are (credentials in `Headers` under the keys `CreatePublisherForTarget` already reads) — the publisher layer is untouched. The `cfg:` prefix cannot collide with a Secret target (those are DNS-1123-validated), so no precedence logic exists. Deterministic order and naming, so a reload produces byte-identical names.
  - **One merged view** (`DefaultTargetDiscoveryManager`): a second, separately swapped cache holds config targets, so `ListTargets`/`GetTarget`/`GetTargetsByType` return the union while the K8s path stays bit-for-bit unchanged and a Secret refresh can no longer wipe config targets. The swap is atomic — a reload never exposes a window with zero targets. New `source="config"|"k8s"` label on the discovery gauge, `targets_by_source`/`targets_config` on the stats collector, `DiscoveryStats.ConfigTargets`.
  - **Startup + reload wiring**: built from the loaded config before the publishing mode manager's first transition check (so a config-only deployment does not start metrics-only), rebuilt on every reload (the routing fingerprint already fires on receivers-only edits). The **lite profile** now runs the real publishing stack in config-only mode — no K8s client, no Secret discovery, no periodic refresh — whenever the config carries receiver integrations.
  - **`global:` endpoint fallbacks**: new `global.slack_api_url` / `global.pagerduty_url` / `global.telegram_api_url`, resolved into any integration that omitted its own endpoint at parse time (per-integration value always wins). A `slack_config` with neither its own `api_url` nor the global one is a load error naming both places; `email_configs` without `global.smtp_smarthost` / `smtp_from` likewise (AMP models no per-`email_config` SMTP fields).
  - **`send_resolved` per integration** (upstream default true): carried as `filter_config.send_resolved` and applied during target resolution in `PublishingCoordinator`, so a suppressed notification never enters the queue (no job, no retry, no breaker effect). A resolved-only group reaching a `send_resolved: false` target is a no-op with no notification-log entry — upstream's own dedup-stage outcome. K8s targets can use the same key. Side effect: the fully-deduped steady state no longer returns "no targets found for receiver", which the notify chain used to log as a publish error on every fire.
  - **Blackhole receivers** (upstream's `- name: 'null'`): a receiver declared with no deliverable integration is valid, loads, and drops what is routed to it as a SUCCESSFUL notification (the group settles instead of re-firing every `group_interval`), counted as `alert_history_publishing_blackhole_drops_total{receiver}`. Covers a receiver whose only block is `opsgenie_configs`/`victorops_configs`/`wechat_configs`, which also gets a load-time WARNING naming the unsupported integration. A route pointing at an undeclared receiver stays a loud error.
  - **Receiver scoping on the non-grouped publish path** (review finding C1): `services.Publisher` used to fan every alert out to every target whenever `grouping.enabled` was false (the default) or grouping failed open — harmless with hand-made Secrets, a cross-receiver leak once every integration provisions a target. - **AMP-PARITY-WAVE4** (2026-08-19): wave-4 follow-ups on top of the parity epic.
  - **Per-alert outcome tracking for non-batch publishers** (`FU-PER-ALERT-OUTCOMES`, the wave-3 M4 residual): a partial per-alert failure no longer re-sends the alerts that already landed. Slack/Telegram/PagerDuty/Email have no array-payload wire shape, so one group job loops `Publish` once per alert; before this, alert 3 of 5 failing made the whole `(group, target)` pair unconfirmed, no nflog entry was written, and the group's next fire re-sent all five — duplicating the four that had been delivered. Exactly-once per `(alert, target)` within a notification cycle is now the goal, with at-least-once still the floor.
    - **The job reports which alerts landed**: `PublishingQueue.publishJob` tracks accepted alerts per job and skips them when the same job is retried (previously every in-job retry resent the whole set), publishing an immutable snapshot readable through `GroupPublishHandle.DeliveredAlerts` *while the job is still running* — so even a job whose confirmation wait expired hands back the progress it made. `PublishingResult.DeliveredAlerts` / `grouping.TargetPublishOutcome.DeliveredAlerts` carry it up the chain, and are empty for confirmed targets (the full nflog entry supersedes them) and for batch targets (one atomic POST has no partial state).
    - **The chain stores it and narrows the retry**: `GroupNotifyLog` gains `DeliveredAlerts` / `RecordPartialDelivery`, backed by a new Redis key family `nflog:delivered:{groupKey}:{target}` (HASH `{alert fingerprint → delivered status}`, TTL = `repeat_interval` + 60s grace, capped at 500 alerts, additive across fires, written by a single Lua script so the cap check, the writes and the TTL are atomic) and by an expiring map in the in-memory log. `RecordSent` and `Forget` delete it. `publishGroupAlerts` filters each target's alert list against its delivered state (`alertsStillOwed`), so the retry fire carries only the alerts still owed — and the per-target `skipTarget func(string) bool` callback becomes `targetAlerts func(string, []*core.Alert) []*core.Alert`, whose empty result is the old "skip this target".
    - **Compared by `core.Alert.DeliveryKey` (`fingerprint:status`)**, hoisted out of `grouping.alertSetSignature` so the delivered state and the nflog signature are built from the same atoms: matching is never positional (a group legitimately gains and loses alerts between fires) and an alert that flipped `firing`↔`resolved` counts as new and is re-sent. **Stored one status per fingerprint**, so recording an alert's new status replaces the previous one — an alert flapping `firing→resolved→firing` must be delivered again, and keeping both statuses would have suppressed the re-fire for up to a `repeat_interval`. Cross-replica by construction, so a replica adopting the group mid-recovery re-sends the same remainder.
    - **Fails open in the resend direction**: a delivered-state read/write error, or hitting the cap, degrades to the pre-wave-4 behaviour (re-send everything) rather than suppressing an alert; cap refusals are counted as `amp_group_operations_total{operation="delivered_state",status="capped"}` so the reversion is visible. Upstream honesty: upstream Alertmanager has no per-alert send at all (one wire message per `group × integration`), so this whole mechanism is an AMP extension, documented as such in `docs/ALERTMANAGER_COMPATIBILITY.md`.

    - **`AbandonReasonShutdown` is now reachable** (review finding M-b): `PublishGroupToTargets` distinguishes an explicitly-cancelled context (`context.Canceled` — shutdown, or a caller giving up for a reason unrelated to the target) from the caller's own bounded deadline expiring (`context.DeadlineExceeded`, still `AbandonReasonUnconfirmed`). Previously a real `SIGTERM` cancelling the grouping context made every in-flight target's abandonment default to `Unconfirmed`, tripping one spurious circuit-breaker failure per target on every shutdown.
    - **A genuine failure racing the confirmation-wait timeout keeps its DLQ entry** (review finding M-c): the queue's abandon-branch check now requires the job's own returned error to wrap `context.Canceled` (extracted into `jobWasAbandoned`), not merely that `job.ctx.Err() != nil` — a job whose final HTTP attempt settles (success, or a real 500/refused failure) at essentially the same instant the waiter's timeout fires no longer gets silently reclassified as "abandoned" and losing its DLQ write.

An explicit operator value still wins, and `validateNotifyTimingBudget` still guards the result.

- **AMP-PARITY-WAVE3** (2026-08-19): wave-3 reliability follow-ups on top of the parity epic.
  - **`RecordSent` follows CONFIRMED delivery** (`FU-RECORDSENT-DELIVERY-CONFIRMATION`): a publishing-queue job can now carry a completion channel signalled exactly once with its final outcome (`PublishingQueue.SubmitGroupWithConfirmation`), and `PublishingCoordinator.PublishGroupToTargets` blocks on it per target — so `TargetPublishOutcome.Success`, and therefore the per-`(group, receiver, target)` nflog entry, means "the target's HTTP call succeeded" instead of "a job was enqueued". A webhook answering 500 after enqueue no longer gets a dedup entry and is re-published on the group's next scheduled fire instead of staying suppressed for a whole `repeat_interval`. Metrics-only mode, an open circuit breaker and a publisher that cannot be built all report `ErrDeliveryNotAttempted` (no entry, retried); a wait that exceeds the confirmation timeout reports `ErrDeliveryWaitTimeout`, is also treated as unconfirmed (keeping the pipeline at-least-once), and **abandons** the job so a hanging endpoint cannot pin workers.
    - **One time budget, one knob**: new `publishing.queue.delivery_confirmation_timeout` (45s default, 2m maximum) drives the per-target wait, and the grouping side derives its timer-callback deadline (60s), cross-replica publish-claim TTL (65s) and orphan-adoption grace (90s, was 20s) from it (`grouping.TimerCallbackTimeoutFor` / `NotifyLogClaimTTLFor` / `ReconciliationGraceFor`). `ServiceRegistry.validateNotifyTimingBudget` refuses to start on an inconsistent set and logs the whole budget, including the deliberately-shorter timer lock TTL. Previously these were independent literals and the shortest (a hardcoded 30s timer-callback context) silently capped every delivery; the too-short adoption grace additionally let a live fire be adopted, whose `DeleteTimer` raced the publisher's continuation `SaveTimer`.
    - **Post-delivery bookkeeping survives a long fire**: `RecordSent`, the claim release and resolved-alert pruning run on contexts detached from the fire's own, each created *after* the delivery wait returns (a detached context created before the wait has its deadline consumed by the wait — the same bug in disguise). `RedisNotifyLog.TryClaim` and `RedisTimerStorage.AcquireLock` release closures likewise derive their own contexts at release time instead of capturing the acquiring one.
    - **Abandonment is classified**: `GroupPublishHandle.Abandon(reason)` — a waiter-timeout abandonment counts as a circuit-breaker failure (so a target that *hangs*, and therefore never produces a failed job, still opens its breaker) and is exported as `jobsProcessedTotal{status="abandoned_unconfirmed"}`; shutdown-driven cancellation counts against nothing. Abandoned jobs are never written to the DLQ, since the notify chain re-publishes to unconfirmed targets.
    - **Per-group publish lock**: the notify chain's `publishGroupAlerts` lock is a refcounted per-`GroupKey` entry instead of a 256-way striped mutex — with a blocking delivery inside the critical section, two hash-colliding group keys would otherwise serialize for a full confirmation timeout.
    - Also fixes a pre-existing data race in `PublishingQueue.submitJob`, which called `JobTrackingStore.Add` (reading `job.State`/`job.StartedAt`) after handing the job to a worker.

### Breaking changes / migration notes
- **A route without `group_by` now groups upstream-style: ONE notification per receiver, not one per `alertname`** (post-merge fix for `FU-RECEIVERS-INTEGRATION`): `business/routing.TreeBuilder.inheritGroupBy` used to substitute `["alertname"]` when neither the route, its ancestors, nor `global.group_by` set it. Upstream Alertmanager's `DefaultRouteOpts` leaves `group_by` EMPTY, which means every alert the route matches aggregates into a single group whose labels are `{}` — that is what `GET /api/v2/alerts/groups` and `amtool` report, and what the notify chain sends. **If you relied on the implicit per-`alertname` grouping, set `group_by: [alertname]` explicitly** (upstream requires the same). Affects only configs that never specify `group_by` at any level; every config with an explicit `group_by` is unchanged. This divergence pre-dated the epic and was masked: a `route:`/`receivers:` config with an integration-less receiver failed to load before blackhole receivers became legal, so the groups API fell back to its legacy single-synthetic-group path and the upstream-parity test passed for the wrong reason.
- **PagerDuty Events API v2 endpoint corrected** (`FU-RECEIVERS-INTEGRATION`, slice 1): the publisher posted trigger/acknowledge/resolve events to `<base>/v2/events`, which is not a PagerDuty endpoint — Events API v2 enqueues at `<base>/v2/enqueue`. Every PagerDuty notification was rejected. Nothing to change for real PagerDuty targets (they start working), but **any mock, proxy or self-hosted listener built against the old path must now serve `/v2/enqueue`** (change events keep using `/v2/change/enqueue`). A target URL carrying the FULL endpoint (`https://events.pagerduty.com/v2/enqueue`, upstream's `pagerduty_configs[].url` semantics — or `/v2/events`, if a Secret was written to compensate for the bug) is normalised to its base before the path is appended, so both existing K8s Secret shapes keep working without edits.
- **Renaming the ROOT route's receiver needs a restart** (`FU-RECEIVERS-INTEGRATION`, slice 1): the degraded-routing fallback receiver (used only when a configured route tree produced no decision — a non-fatal tree build failure or a per-alert `Evaluate` error) is a startup snapshot of `route.receiver`. After a reload that RENAMES it, that fallback points at a name the config no longer declares, so degraded-state alerts fail loudly (`routing unavailable` / `no targets found for receiver`) instead of being delivered — a safe failure mode, but it stays until the process restarts. Same restart class as adding a `route:` section to a config that started without one. Normal (non-degraded) routing follows the reload immediately.
- **`email_configs` now REQUIRE global SMTP settings — a previously-loadable config can fail to boot** (`FU-RECEIVERS-INTEGRATION`, slice 2): a receiver declaring `email_configs` must have `global.smtp_smarthost`, plus either `global.smtp_from` or a `from` on every entry. Two shapes that loaded before (with a WARN, and silently provisioned no email target) now fail validation at startup AND on `/-/reload`, so an upgrade can turn a running deployment into a boot loop: (1) `email_configs` with no `global.smtp_*` block at all; (2) an upstream config that sets SMTP **per `email_config`** (`smarthost`/`auth_username`/`auth_password`/`require_tls`) — AMP models no per-integration SMTP fields, so those keys are dropped by the parser and cannot substitute for the global ones. Fix in one line: add `global.smtp_smarthost` (and `global.smtp_from`) to your config. This matches upstream Alertmanager, which fails `config.Load` with "no global SMTP smarthost set" / "no global SMTP from set" for the same shape; the alternative (warn and blackhole) is silent non-delivery of email.
- **Receiver names must be unique** (`FU-RECEIVERS-INTEGRATION`, slice 1): duplicates are now a load error, as in upstream Alertmanager. A config with two receivers of the same name previously loaded and silently used only one of them.
- **A receiver with no integrations is now valid** (`FU-RECEIVERS-INTEGRATION`, slice 1): upstream's blackhole receiver (`- name: 'null'`) and a receiver whose only integration AMP cannot deliver (`opsgenie_configs`, `victorops_configs`, `wechat_configs`) load instead of failing validation, emit a load-time WARNING naming the unsupported integration, and drop notifications routed to them (counted as `alert_history_publishing_blackhole_drops_total{receiver=...}`). configvalidator's `E024` became the non-blocking `W024`.
- `services.Publisher`'s methods were renamed `PublishToAll`/`PublishWithClassification` → `PublishToReceiver`/`PublishToReceiverWithClassification` and now take the routed receiver: the non-grouped publish path (the default, `grouping.enabled: false`) used to fan every alert out to every target regardless of receiver.
- Receiver names must not contain `/` (reserved as the group-key separator, `receiver=<name>/<group-key>`); any other non-empty name is accepted.
- `GET /api/v2/status`'s `config.original` now redacts secret-named fields (PagerDuty `routing_key`, Slack/webhook URLs, Telegram `bot_token`, etc.) with upstream's own `<secret>` placeholder instead of the raw config.
- `PagerDutyConfig.RoutingKey` validation relaxed from `validate:"len=32"` to `validate:"required"`, matching upstream's plain non-empty `Secret` type — any previously-32-char-enforced config still validates, but non-32-char keys that were wrongly rejected before now pass too.
- `DELETE /api/v2/silence/{id}` expires the silence in place (upstream-like semantics) rather than a hard delete; treat it as "mark expired now," not row removal.
- Old bare group-level nflog Redis entries (`nflog:entry:{groupKey}`) are never read by the new target-suffixed lookup (`nflog:entry:{groupKey}:{target}`) and simply expire on their original TTL — no migration step needed.
- `grouping.reconciliation_grace` default changed 20s → 90s (derived from `delivery_confirmation_timeout`), and startup now **fails** on a pinned value that is not strictly greater than the publish-claim TTL (65s at defaults): a config carrying the old `reconciliation_grace: 20s` must raise it (or drop it to inherit the derived default).
- HA failover recovery time grew accordingly: a crashed replica's groups are adopted after up to ~90s grace + one reconciliation tick (was ~20s + tick) — the price of closing the mid-flight adoption race (`DeleteTimer` vs the live publisher's `SaveTimer`).
